# pyRPC System Design

## Package Architecture

```
npm install @pyrpc/client
        │
        ▼
┌─────────────────────────┐
│  @pyrpc/client          │  TypeScript client (npm)
│  @pyrpc/types           │  Generated type defs (postinstall)
└─────────────────────────┘
        ▲
        │  GET /rpc (JSON-RPC schema)
        │
┌─────────────────────────┐
│  Adapters               │
│  pyrpc-fastapi          │  Framework HTTP → Interpreter
│  pyrpc-flask            │
└─────────────────────────┘
        │
        ▼
┌──────────────────────────────┐
│  pyrpc-core (runtime + CLI)  │
│  ───────────────────────     │
│  Protocol, router, validation│
│  pyrpc serve                 │  ASGI dev server
│  pyrpc dev                   │  Dev console (watcher + REPL)
│  pyrpc inspect               │  List procedures
│  pyrpc codegen               │  Generate TypeScript types
│  pyrpc pull                  │  Export schema as JSON
└──────────────────────────────┘
        │
        ▼
┌─────────────────────────┐
│  pyrpc-codegen           │  Pure library: jinja2 + jsonschema-ts
│  ───────────────────     │
│  ts_codegen.py           │  Template rendering, type mapping
└─────────────────────────┘
```

### Dependency Direction

```
pyrpc-core → pyrpc-codegen
(no pyrpc deps)   (no pyrpc deps)
```

- `pip install pyrpc-core` → installs everything (runtime + CLI + codegen)
- CLI is embedded directly in pyrpc-core (no separate pyrpc-cli package)
- pyrpc-codegen is a pure library with zero CLI or web dependencies

## Package Evolution

Originally pyrpc was split into three packages (core, cli, codegen) to break a
circular dependency between core and codegen. After stripping pyrpc-codegen into
a pure library (no core dependency), the circular dep no longer existed, so the
CLI was merged back into pyrpc-core for a simpler single-install experience.

```
Before (3 packages):  pyrpc-core → pyrpc-cli → pyrpc-codegen
After (2 packages):   pyrpc-core → pyrpc-codegen
```

## CLI Layering

### Command Tiers
```
Tier 1 (No core import):  version, help
Tier 2 (Core import):     serve, dev, inspect
Tier 3 (Codegen import):  codegen, pull
```

Lazy imports ensure:
- `pyrpc version` starts instantly (no core loaded)
- `pyrpc codegen` only loads codegen when needed
- Failures in one tier don't break other tiers

### First-Run Setup (pyrpc serve)
On first `pyrpc serve` (no config found):
1. Prompt for framework (FastAPI / Flask / ASGI)
2. Prompt for entry point module
3. Auto-install adapter: `pip install pyrpc-fastapi`
4. Write `[tool.pyrpc]` to `pyproject.toml`

Pass `--reconfigure` to re-run setup.

## Dev Console Architecture

```
Parent Process
  │
  ├── pyrpc serve (dev server + file watcher)
  │     │
  │     └── HTTP → ASGI → Interpreter.handle_request()
  │
  └── get_registry_schema(default_router)
        │
        ▼
  Embedded REPL (dev console)
    - Reads schema from parent process (not HTTP)
    - Uses code.InteractiveConsole
    - Banners show registered procedures
```

### Key Design Decisions
- **No HTTP loopback**: dev console reads schema via direct function call, not `GET /rpc`
- **Shell connects remotely**: `pyrpc shell` connects to a running server via HTTP
- **File watcher**: `watchfiles` triggers restart on Python file changes

## Adapter Contract

Each adapter (FastAPI, Flask, ASGI) must:
1. Receive HTTP request
2. Parse JSON-RPC 2.0 body
3. Call `Interpreter.handle_request(body, context)`
4. Return JSON response with correct HTTP status

### Constraints
- Adapters must not fork protocol behavior
- Adapters must not add custom validation
- Core is framework-agnostic (no FastAPI/Flask imports in pyrpc-core)

## Configuration

### pyproject.toml (`[tool.pyrpc]`)
```toml
[tool.pyrpc]
framework = "fastapi"
entry_point = "app.main:app"
```

Generated by first-run setup. Read by CLI commands to locate the server.

## Key Decisions

| Decision | Rationale |
|----------|-----------|
| CLI merged back into pyrpc-core | After pyrpc-codegen became a pure library, the circular dep no longer existed — the middle package was removed |
| Two packages not three | CLI merged back into core after codegen became a pure library; middle package removed |
| No meta-package (`pyrpc` taken) | `pyrpc` already claimed on PyPI; `pyrpc-core` is the entry point |
| Lazy imports for tiered CLI | Faster startup for basic commands, clean error isolation |
| Dev console reads parent process | Avoids HTTP dependency during development |
| `[tool.pyrpc]` in pyproject.toml | Follows FastAPI `[tool.fastapi]` convention |
| Lockstep versioning | All packages release at same version; enforced by release script |
